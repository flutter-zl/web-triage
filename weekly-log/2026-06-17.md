### #187561 — [Web] Autocomplete loses keyboard focus after options appear when ensureSemantics() + MaterialApp.router are used
- **Action**: triage
- **Priority**: P1
- **Suggested assignee**: flutter-zl
- **Labels to add**: triaged-web, P1
- **Labels to remove**: (none — keep existing)
- **Comment**: (none needed — mbcorona already routed it)
- **Reasoning**: Confirmed regression (works in 3.38.10, broken in 3.41.3+), customer escalation via `customer: caboose`, reproducible on DartPad, web-only.
- **Root cause**: When the Autocomplete options overlay is inserted into the semantics tree in semantics mode, a newly created semantics DOM node fires a browser focus event that pulls keyboard focus away from the active `<input>`. The framework then receives a `ViewFocusEvent` or DOM blur from the semantics layer and clears text field focus. The regression window (3.38–3.41) coincides with changes to how the semantics tree handles overlay/route insertions.

### #187939 — [web] Initial ViewFocusEvent races first layout: focus traversal throws 'RenderBox was not laid out' at startup
- **Action**: triage
- **Priority**: P1
- **Suggested assignee**: flutter-zl
- **Labels to add**: triaged-web, P1
- **Reasoning**: Affects every page load for apps with focusable widgets, confirmed in production, detailed decoded root cause provided. Pollutes console and error monitoring on every single load.
- **Root cause**: The engine delivers the initial `ViewFocusEvent(focused, forward)` before the framework's first layout pass completes. `FocusManager` immediately calls `ReadingOrderTraversalPolicy._sortAllDescendants`, which reads `FocusNode.rect` → `RenderBox.size` on nodes that have been attached but not yet laid out, causing a `Bad state: RenderBox was not laid out` throw. Fix: defer ViewFocusEvent handling to `addPostFrameCallback` during startup, or guard traversal against unlaid-out render objects.

### #187532 — Web does not correctly identify first stylus button press
- **Action**: triage
- **Priority**: P2
- **Suggested assignee**: (blank — no clear owner in stylus/pointer area)
- **Labels to add**: triaged-web, P2, has reproducible steps (already present), engine
- **Reasoning**: Clear repro, contributor has investigated root cause and wants to contribute a fix. Web-specific pointer event button mapping bug.
- **Root cause**: Flutter Web's pointer event handler in the engine maps stylus barrel button state using the wrong bit mask. The Web Pointer Events API uses `0x20` (bit 5) for the first barrel button, but Flutter's web engine interprets this as `0b100000` instead of normalizing it into Flutter's `kPrimaryButton | kSecondaryButton` convention. The `0x32` value mentioned is the eraser detection bit — that should map to `PointerDeviceKind.stylus` with `buttons` reflecting eraser contact.
