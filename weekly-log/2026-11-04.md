### #195700 - `flutter test --platform=chrome` per-suite load time regressed ~40% after `--no-js-strongly-connected-components`
- **Action**: re-route
- **Priority**: P1
- **Suggested assignee**: blank, re-route. Markzipan authored #193485 and is the natural owner of the workaround
- **Labels to add**: team-tool, fyi-web, P1, found in release: 3.50
- **Labels to remove**: team-web, in triage
- **Reasoning**: elliette traced the step change to #193485, a `tool` PR that turned on per-library DDC output, which takes material_ui web tests in flutter/packages past the 90 minute timeout and blocks the flutter/flutter to flutter/packages roller. The tests are disabled for now in flutter/packages#13537, so this is P1 rather than P0. The change lives in flutter_tools and the DDC team is already discussing it.
- **Root cause**: the web test runner loads each suite in its own iframe, so going from about 1053 to 1537 scripts per suite is paid once per test file. #193485 improves large app load time but makes the per-suite cost of `--platform=chrome` worse.
- **Potential solutions**: (1) Turn `--no-js-strongly-connected-components` off for `--platform=chrome` test compiles only, which the DDC team already suggested. (2) Decide whether `--platform=chrome` stays supported, given the comment in `packages/flutter_tools/lib/src/commands/test.dart` that it may be removed. (3) Longer term, share loaded modules across suites instead of reloading the app per iframe.

### Text input, currently on `team-web`

### #195741 - [web] Android Chrome "Desktop site": keyboard Next in an AutofillGroup focuses a hidden autofill input, so TextInputAction.next never fires
- **Action**: re-route
- **Priority**: P2
- **Suggested assignee**: blank, re-route. mdebbar if the web team keeps it
- **Labels to add**: team-text-input, fyi-web, P2, browser: chrome, has reproducible steps, found in release: 3.47
- **Labels to remove**: team-web
- **Reasoning**: clear repro and source-level analysis on two Pixel Tablets and a Pixel 8. Desktop site is the default on large Android tablets, so login forms with `AutofillGroup` break there by default. mbcorona sent it straight to `team-web`, but the guide routes text input to `team-text-input`. Related: #180144, #100708. No linked PR.
- **Root cause**: in Desktop site mode the user agent says Linux, so `EngineInputAction.configureInputAction` sets no `enterkeyhint`. Chrome then handles the IME Next action by moving focus to the next text control in the form, which is the engine's hidden autofill password input because it has no `tabIndex = -1`. `DefaultTextEditingStrategy.handleBlur` pulls focus back and no keydown ever reaches the engine.
- **Potential solutions**: (1) Set `tabIndex = -1` on the hidden autofill inputs in the engine's form so Chrome does not treat them as the next field. (2) Set `enterkeyhint` and `inputmode` on every platform rather than only on detected mobile ones. (3) Detect Android in desktop mode with `maxTouchPoints` plus an ARM `navigator.platform`.

### #195774 - [web][iOS] Rotating with the keyboard up sets viewInsets.bottom to 0, so the app is laid out behind the keyboard and the caret is not revealed
- **Action**: triage
- **Priority**: P2
- **Suggested assignee**: mdebbar
- **Labels to add**: triaged-web, P2, browser: safari, found in release: 3.47
- **Labels to remove**: none
- **Reasoning**: measured repro on an iPhone 14, confirmed from source by mbcorona. It carries `a: text input`, but the bug is in view metrics in `window.dart`, not in text editing, so it stays on `team-web`. Rotating with the keyboard open is common on phones and leaves the caret hidden until the keyboard closes. Related: #160505. No linked PR.
- **Root cause**: `EngineFlutterView._handleBrowserResize` computes `isEditingOnMobile` as `_shouldPreservePhysicalSizeOnResize && !_isRotation(...)`, so a rotation forces it false and `_computeOnScreenKeyboardInsets` returns 0 even while editing. Safari sends a single `visualViewport` resize per rotation, so nothing corrects the inset afterwards.
- **Potential solutions**: (1) On rotation, still compute keyboard insets from `visualViewport` when a text field is active, and only reset the preserved physical size. (2) After a rotation, schedule one more metrics pass once the viewport settles.

### Semantics and text field focus

### #195763 - [web] Semantics on: mouse click on a button next to a focused TextField leaves EditableText focused but engine editing off
- **Action**: re-route
- **Priority**: P2
- **Suggested assignee**: blank, re-route. flutter-zl owns the engine code if `team-accessibility` hands it back
- **Labels to add**: team-accessibility, fyi-web, P2, has reproducible steps, found in release: 3.47
- **Labels to remove**: team-web
- **Title cleanup**: `[web] With semantics on, a mouse click on a button next to a focused TextField stops typing in the field`
- **Reasoning**: 10 of 10 repro in Playwright with real Chrome input, confirmed from source by mbcorona. A clear button next to a search field is very common. Accessibility comes first in the routing order. Same family as #195289 and #195291 from last week. No linked PR.
- **Root cause**: `_isIntegerCoordinateNavigation` in `EnginePlatformDispatcher` treats any click with whole-number coordinates on a button as an assistive technology activation and focuses the button, but desktop Chrome reports whole-number coordinates for ordinary mouse clicks at DPR 1. The resulting blur queues a deferred `safeBlur` that runs after the framework has re-enabled editing, and moves focus to the view root.
- **Potential solutions**: (1) Use `PointerEvent.pointerType`, `detail == 0`, or the absence of a preceding `pointerdown` as the assistive technology signal instead of integer coordinates. (2) Cancel or re-check the deferred `safeBlur` when the element is enabled or focused again before it runs. (3) Fix together with #195291 through a shared blur handler that refocuses the `<input>` while the connection is still open.

### #195812 - [web] With semantics on, a click on a text field's `<input>` that has no pointer events before it also sends `SemanticsAction.tap` to a tappable ancestor
- **Action**: triage
- **Priority**: P2
- **Suggested assignee**: flutter-zl
- **Labels to add**: triaged-web, P2, engine, platform-web, found in release: 3.47
- **Labels to remove**: none
- **Reasoning**: already on `team-accessibility` with `fyi-web`, so it keeps its routing. Reproduced on master in five browsers. A tap-outside-to-dismiss `GestureDetector` around a form is a common pattern, and VoiceOver activation on WebKit builds before 322978@main sends exactly this event shape. No linked PR.
- **Root cause**: the `SemanticTextField` click listener in `lib/web_ui/lib/src/engine/semantics/text_field.dart` focuses the `<input>` but does not stop propagation. The click bubbles to the ancestor `Tappable`, and `ClickDebouncer` sees no recent `pointerup` and sends `SemanticsAction.tap` for the ancestor, which unfocuses the field.
- **Potential solutions**: (1) Call `event.stopPropagation()` in the text field's click listener, matching what `_sendSemanticsTapToFramework` already does for nested tappables since #134842. (2) Add a test with a tappable ancestor that dispatches a bare `click` on the `<input>`.
