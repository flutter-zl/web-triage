### #185727 - [Web Mobile] Stuttering when flick scrolling
- **Action**: triage
- **Priority**: P2
- **Suggested assignee**: flutter-zl
- **Labels to add**: `triaged-web`, `P2`, `browser: chrome`
- **Labels to remove**: (none)
- **Reasoning**: Already labeled `c: performance`, `f: scrolling`, `has reproducible steps`, `platform-web`, `team-web` from mbcorona's pre-routing. Per the routing table, scrolling on web is mine. Reproduces on Galaxy S24 mobile Chrome regardless of `--wasm`, so add `browser: chrome` (and note that `--wasm` makes no difference, so the issue is renderer-agnostic). High refresh rate display required to see the stutter; reporter provided a 100fps capture.
- **Root cause**: Flick (fling) scrolling on Flutter Web mobile diverges from drag scrolling because drag scrolls drive the scrollable directly through pointer events on each frame, while fling scrolls run the deceleration animation through the framework's `BallisticScrollActivity` and translate that into per-frame Dart-side updates. On a 120 Hz Galaxy S24, the browser's compositor scrolls at the panel rate but Flutter's engine-driven scroll updates are paced by `Window.onBeginFrame` callbacks that don't always align with the browser's vsync, so we visibly drop frames during the fling tail. Drag scroll feels smooth because it's pointer-driven (one event per OS sample). Worth investigating whether the fling is animated by `Scheduler.scheduleFrame` rather than the browser's native momentum scroll, and whether we can hand fling animation back to the browser (the same direction the `flutter-browser-scroll` package explores). Renderer-agnostic, so this is an engine-level scheduling/animation issue rather than a paint/raster issue.

### #185931 - [web][canvaskit] Safari 26.5 / WebKit 21625: scroll views render with huge gaps between widgets
- **Action**: triage
- **Priority**: P2
- **Suggested assignee**: harryterkelsen
- **Labels to add**: `triaged-web`, `P2`, `e: web_canvaskit`, `engine`
- **Labels to remove**: (none)
- **Reasoning**: Already labeled `c: regression`, `browser: safari-macos`, `has reproducible steps`, `platform-web`, `team-web`. Visual regression in CanvasKit-rendered scroll views, only on Safari 26.5 beta / WebKit 21625; works fine on Safari 26.4. mbcorona confirmed they could not reproduce on 26.4. Switching renderer to skwasm did not fix it, so this is likely a CanvasKit/Skia interaction with new WebKit behavior rather than a Flutter layout bug. P2 because Safari 26.5 is still in beta — bumps to P1 if it ships in a stable Safari without resolution. Per routing table, CanvasKit/rendering issues are harryterkelsen's. Live repro available at the link, plus screenshot evidence.
- **Root cause**: Reporter notes `<body>` is `position: fixed; inset: 0; width: 1584px; height: 922px; overflow: hidden;` and `<flutter-view>` reports its normal viewport (`1584x884`), so the host container sizing is correct. The breakage is inside the rendered scene: the column of cards is laid out at far larger Y offsets than expected, multiplying the inter-widget gaps. Older Flutter on the same Safari beta works, so this isn't WebKit dropping support for a Flutter-emitted layout. More likely the new WebKit changed how it interprets one of the CSS properties Flutter emits for layered scrollables (e.g. `transform`, `will-change`, or the dimensions of canvases used as Skia surfaces), and the canvas/scene placement now resolves to multiplied offsets. First place to look is `lib/web_ui/lib/src/engine/canvaskit/embedded_views_diff.dart` and the canvas-positioning math in the rasterizer, comparing emitted style strings against what 26.5 actually applies. Also worth checking against an Apple WebKit bugzilla report — if it's a WebKit regression, file there too.

### #185995 - [skwasm] Canvas.drawAtlas crashes "memory access out of bounds" when batch exceeds ~2000 entries (wasm stack overflow in withStackScope)
- **Action**: triage
- **Priority**: P2
- **Suggested assignee**: harryterkelsen
- **Labels to add**: `triaged-web`, `P2`, `c: crash`, `e: web_skwasm`, `e: wasm`
- **Labels to remove**: (none)
- **Reasoning**: Already labeled `has reproducible steps`, `platform-web`, `team-web`. Engine-side wasm crash in skwasm's `Canvas.drawAtlas` for large batches (≥ ~2000 entries), which is the canonical batch size for `package:flame_tiled` tilemap rendering. Reporter provided a thorough root-cause analysis (`withStackScope` + `_emscripten_stack_alloc` budget = 64 KiB Emscripten default; 4096 entries × 36 bytes = 144 KiB → overflow → next `malloc` traps). Reporter has filed PR #185997 with chunking fix and verified locally. P2 because it crashes a real shipping use case (Flame tilemaps) but only on skwasm, with a workaround (`useAtlas: false` or canvaskit). harryterkelsen owner for skwasm/wasm.
- **PR review**: PR #185997 (linked) chunks `SkwasmCanvas.drawAtlas` / `drawRawAtlas` at 1024 entries per native call (~36 KiB worst case, well under 64 KiB stack). The fix addresses the immediate crash directly. The PR description correctly identifies that this is the smallest, most-localised fix and lists two more general alternatives: bumping `STACK_SIZE` in `skwasm/BUILD.gn` ldflags, or adding a heap fallback in `StackScope` itself. The general fix would also cover `drawPoints`, `drawRawPoints`, `drawVertices`, and any future `withStackScope` consumer — but it's reasonable to ship the chunking fix now and follow up with a `StackScope` heap fallback later. Worth pairing the PR with a regression test that runs `drawAtlas` with > 2000 entries on the skwasm test config. Approach is sound; reviewer should ask the author for the regression test and a follow-up issue tracking the `StackScope` heap-fallback general fix.

### #186044 - [Feature Request][Web][A11y] Provide default or configurable visible focus indicator for focusable Flutter Web semantics nodes
- **Action**: re-route
- **Priority**: P2
- **Suggested assignee**: flutter-zl
- **Labels to add**: `triaged-web`, `P2`, `fyi-web`, `c: new feature`, `team-accessibility`
- **Labels to remove**: `team-web`
- **Reasoning**: Per routing table, accessibility issues go to `team-accessibility` with `fyi-web` for visibility. This is a WCAG 2.4.7 compliance gap: Flutter Web's `flt-semantics` nodes are keyboard-focusable (`tabindex="0"`) and exposed with interactive ARIA roles, but the framework does not render a default visible focus ring on them. Reporter included a clean repro (`showDatePicker` flow) and an axe Auditor finding tagged Critical. Bump from default P3 → P2 for feature requests because: (a) it's a WCAG 2.1 AA conformance failure (not just polish), (b) Material widgets like the date picker hit it, so it can affect any Flutter Web app doing keyboard navigation. mbcorona also surfaced a related bug during repro: Shift-Tab from `ElevatedButton` skips the Semantics node and lands the browser URL bar — that's a focus-traversal escape, worth tracking either inside this issue or as a follow-up. Code-wise the fix lives in web_ui's semantics layer (where we set `tabindex` and ARIA roles); we can either render a visible outline directly on the focused `flt-semantics` element or expose a public hook for apps to style it. I'll take ownership.
- **Root cause**: This is web-only (only reproduces on web), so I'm including a note even though routing changes to team-accessibility. Web's semantics layer creates `flt-semantics` elements with `tabindex="0"` for any node that is focusable per the framework's `Focus` system, but does not apply any `:focus`/`:focus-visible` CSS or default outline. Native browsers normally apply a UA default focus ring, but Flutter Web typically resets `outline: none` on `flt-semantics-host` and child elements during the engine's CSS reset, suppressing the UA ring without providing a replacement. Fix is to either (a) explicitly opt back into a `:focus-visible` outline on focusable `flt-semantics` elements in `lib/web_ui/lib/src/engine/dom.dart` / the semantics CSS, or (b) drive the focus indicator from the framework side via a `Focus` configuration that paints a Flutter-side ring while semantics is active. The Shift-Tab → URL bar escape is a separate but related bug in our focus traversal manager (`accessibility_focus_manager.dart` neighborhood) — likely the previous-focus DOM target isn't computed correctly when the start of the traversal chain is a semantics-owned element.
