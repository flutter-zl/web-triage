### #185452 - Flaky test: hot_restart_web_ddc_library_bundle_test.dart fails with SocketException: Address already in use
- **Action**: triage
- **Priority**: P2
- **Suggested assignee**: mdebbar
- **Labels to add**: `triaged-web`, `P2`, `platform-web`
- **Labels to remove**: (none)
- **Reasoning**: Web tool test flake on the macOS `web_tool_tests` shard. Existing labels (`a: tests`, `tool`, `platform-macos`, `c: flake`, `team-web`) are correct. Mdebbar owns test infra / web flakes per the routing table. Discovered after Xcode 26 upgrade, so likely environment-related rather than test-logic-related, but still belongs to web team.
- **Root cause**: The test reserves a port via the OS, then a different process binds to the same port between the reservation and the test's own bind. The `Address already in use` on port 49159 is in the dynamic/ephemeral range, so this is a classic TOCTOU port-allocation race that probably gets worse on Xcode 26 macOS runners where more daemons sit on ephemeral ports. Fix is to retry the bind on `EADDRINUSE` or hold the socket open across the reservation→bind boundary.

### #185614 - RawAutocomplete not working on web when is a child of SelectionArea widget
- **Action**: triage (already re-routed by mbcorona)
- **Priority**: P2
- **Suggested assignee**: (blank — not team-web)
- **Labels to add**: `triaged-web`, `P2`
- **Labels to remove**: (none)
- **Reasoning**: Already carries `team-text-input` + `fyi-web` from mbcorona's earlier re-route, plus `a: text input`, `platform-web`, `has reproducible steps`. Per the workflow rule, when an issue has `fyi-web` but already carries a different `team-*` label, do not change the routing — just add `triaged-web` to close out web team's review. Istiak-Ahmed78's analysis points at TapRegion / Overlay interaction (related to #184232), which is a framework-level text-input concern rather than a web-engine bug.
- **Root cause**: This is web-only (only reproduces on web), so adding the note even though it's routed to text-input. `SelectionArea` uses `TapRegion` to detect taps outside its bounds and dismiss the selection toolbar, but on web the `RawAutocomplete` options view is rendered into a separate `OverlayPortal` DOM subtree outside the `TapRegion`'s widget subtree. Web's hit-testing routes the tap to `TapRegion` first because the overlay is rendered in a different DOM container than the main widget tree, so `SelectionArea` swallows the tap before it reaches the `ListTile` in the autocomplete options. Native platforms don't see this because OS-level hit testing routes through the widget tree, not DOM tree containment. Likely a `TapRegion.groupId` / `OverlayPortal` registration fix in framework.

### #184858 - [web][skwasm] memory access out of bounds in paragraphBuilder_dispose during heavy widget rebuilds
- **Action**: triage
- **Priority**: P2
- **Suggested assignee**: harryterkelsen
- **Labels to add**: `triaged-web`, `P2`, `c: crash`, `e: web_skwasm`, `e: wasm`, `has reproducible steps`
- **Labels to remove**: (none)
- **Reasoning**: Skwasm/Wasm engine crash in the paragraph builder lifecycle. Owner per the routing table is harryterkelsen (CanvasKit, Skwasm, Wasm runtime). gaaclarke already cc'd him in the thread. davidmigloz provided a deobfuscated production stack trace (engine hash `59aa584fdf100e6c78c785d8a5b565d1de4b48ab`, `paragraph_layout` → ~28 Skia frames → allocator `malloc` → free-list walk traps), which qualifies for `has reproducible steps` per the workflow (production stack trace with deobfuscated frames + root cause analysis). No clean Dart repro yet, but the heap-corruption signature is consistent.
- **Root cause**: davidmigloz's analysis points at the same family of bugs that PR #183022 partially fixed for `SkwasmSurface.rasterizeToImageBitmaps`: a stack-allocated pointer escapes its `withStackScope` lifetime and overwrites heap bookkeeping. The `withStackScope` `assert()` added there is stripped in release wasm-gc builds, so the API still relies on convention. The trap can land in either an allocator walk (allocation side, as in davidmigloz's report) or a free path (`paragraphBuilder_dispose` / `textStyle_dispose`, as in the original report) depending on which allocation reaches the corrupted region first. Audit other Skwasm bindings that take heap pointers from `withStackScope` for the same lifetime escape pattern.
