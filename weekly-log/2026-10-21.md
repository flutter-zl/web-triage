### #194636 - [web][a11y] Focused TextField's text is erased when its semantics node leaves the tree and comes back
- **Action**: triage
- **Priority**: P1
- **Suggested assignee**: flutter-zl
- **Labels to add**: triaged-web, P1, engine, found in release: 3.47
- **Labels to remove**: none
- **Title cleanup**: `[web][a11y] Focused TextField text is erased when its semantics node is removed and re-added`
- **Reasoning**: user data loss, not an announcement problem. Triggers from ordinary events such as scrolling a focused field off screen or a layout breakpoint change. Reproduced on stable and master by the reporter aerotech-vadb and confirmed by mbcorona with a code trace. No linked PR.
- **Root cause**: when the node is disposed, `SemanticTextField.dispose()` calls `SemanticsTextEditingStrategy.deactivate()`, which sets `lastEditingState = null` at `text_field.dart:163` without telling the framework the connection closed. On re-add a new empty `<input>` is created, `enable()` only restores a non-null `lastEditingState`, and Chrome's `selectionchange` on the empty input makes `handleChange()` send `EditingState(text: '')` to the framework.
- **Potential solutions**: (1) Preserve `lastEditingState` across a deactivate while `HybridTextEditing.isEditing` is still true, so re-activation re-applies it. (2) Seed the new semantics `<input>` from `semanticsObject.value` and selection, which is also the #194548 fix. (3) In `handleChange()`, do not treat the first DOM read as a user edit when `lastEditingState` is null. This alone only postpones the loss, so pair it with 1 or 2.
- **Demo**: https://flutter-demo-07-before.web.app, source `flutter-demo-apps/working on/issue_194636_before/`. The reporter's sample with a label and app bar added. Semantics is on at startup, no placeholder click needed.
  - **Steps**: in desktop Chrome, click the text field, which holds `hello`, and optionally type ` world`. Scroll the list down with the mouse wheel until the field is off-screen, then scroll back up.
  - **Bug**: the field is empty and the bottom bar reads `controller.text = ""`. The field is still focused, so the next keystroke continues from the empty value. Fixed: the field still shows `hello world` and the bottom bar matches.
  - **Control**: the same steps with semantics off keep the text. A `MutationObserver` on `<body>` shows the `<input>` after the round trip is a new element with `value=""`, matching the issue's trace.

### #194549 - [web] SemanticScrollable sets scrollTop before resizing its overflow, so the browser clamps it

- **Priority**: P2
- **Suggested assignee**: flutter-zl
- **Labels to add**: triaged-web, P2, engine, f: scrolling, found in release: 3.47
- **Labels to remove**: none
- **Reasoning**: reproduced by suryaKommana2662 with Playwright. Visible jump when a screen reader scrolls after a same-frame extent growth plus jump, which is what type-ahead lists and `ensureVisible` do. No linked PR.

  console.log(sc.scrollTop); sc.scrollTop -= 40;

- **Title cleanup**: `[web] CanvasKit mipmap generation for downscaled images crashes the GPU process on ChromeOS PowerVR Rogue devices since 3.47`

Reported by Gynzy, a known Flutter web customer, with a live repro and a bisected cause. The only workaround is monkey patching CanvasKit in `flutter_bootstrap.js`. No linked PR.
- **Root cause**: `drawImageRect` now uses `kFast_SrcRectConstraint`, so `toSkMipmapMode(FilterQuality.medium)` returning `MipmapMode.Linear` finally takes effect and every downscaled image gets a GPU-generated mipmap chain, roughly 33 percent extra texture memory per image. - **Potential solutions**: (1) Add an engine configuration flag to disable mipmaps on web so affected apps can opt out. (2) Only generate mipmaps above a downscale ratio threshold, and skip them above a texture size cap. (3) Detect PowerVR Rogue via the WebGL renderer string and fall back to `MipmapMode.None`.
