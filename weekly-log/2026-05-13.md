### #186317 - [web]: release-mode main view freezes after first paint until window resize; overlays keep painting
- **Action**: triage
- **Priority**: P1
- **Suggested assignee**: harryterkelsen
- **Labels to add**: `triaged-web`, `P1`, `c: performance` (covers the paint hang per the guide), `browser: chrome`, `found in release: 3.41`
- **Labels to remove**: (none)
- **Reasoning**: mbcorona reproduced locally using the supplied recipe; routed to team-web. Already has `engine`, `platform-web`, `c: rendering`, `has reproducible steps`, `team-web`. Reporter ruled out hosting layer, compression, HTTPS, HTTP/2, both renderers (`canvaskit` and `--wasm`), `dart2js-optimization=O1..O4`, splash overlay timing, google_fonts lazy fetch, and rebuilt-once `LlmClient` caching. Only an actual viewport-metrics change wakes the renderer; `scheduleFrame`, `handleMetricsChanged` from Dart, synthetic resize events, and `notifyListeners` storms all fail. Overlays paint normally throughout, so framework dirty tracking is fine — this is an engine-level paint-scheduling bug specific to the main view's `PipelineOwner` in release. Bumping to P1 because it's release-only and silently freezes any app that hits the trigger condition, with no workaround except telling users to resize the window.
- **Root cause**: The main view's frame request is not being re-armed after some condition during the first frame in release mode; only a real `onMetricsChanged` event from the browser flips the renderer back to scheduling paints. Overlays go through a separate scheduling path (their own owner / repaint boundary), which is why they keep painting. Likely a release-only short-circuit in `EnginePlatformDispatcher` / `FlutterView` frame-scheduling — something that asserts in debug but silently no-ops in release. Worth bisecting between 3.41.5 (or whenever the reporter last saw it work) and 3.41.9 on the paint-scheduling path; specifically inspect `lib/web_ui/lib/src/engine/platform_dispatcher.dart` and `lib/web_ui/lib/src/engine/window.dart` for asserts that gate a `scheduleFrame()` call.
