### Android Chrome keyboard and OS detection, `team-web`

### #196582 - [web][Android] Chrome's desktop site, the default on large Android tablets, is detected as Linux
- **Action**: triage
- **Priority**: P2
- **Suggested assignee**: mdebbar
- **Labels to add**: triaged-web, P2, engine, has reproducible steps, workaround available, browser: chrome-android, found in release: 3.47, found in release: 3.50
- **Labels to remove**: a: desktop
- **Reasoning**: the reporter verified it on 3.50.0, and suryaKommana2662 accepted it. Desktop site is Chrome's default on large tablets, so `inputmode`, `enterkeyhint`, `viewInsets` and `ThemeData` defaults are all wrong there out of the box. `a: desktop` is wrong, because the device is a tablet. This is the root cause behind #195741 from November 4, whose third potential solution was exactly this detection fix, so cross-link them.
- **Root cause**: `detectOperatingSystem` in `engine/src/flutter/lib/web_ui/lib/src/engine/browser_detection.dart` finds Android only through "Android" in the user agent, and the desktop-site UA says X11 Linux. `navigator.platform` keeps Chrome's frozen Android value, `Linux armv81`, and `maxTouchPoints` is above 0.
- **Potential solutions**: (1) Before the Linux branch, check `navigator.platform == 'Linux armv81' && maxTouchPoints > 0` and return Android, mirroring the iPad check from flutter/engine#25957. (2) Pair that with the `tabIndex = -1` fix from #195741, so hidden autofill inputs stay out of the IME's Next order even when detection misses.

### #196303 - [web][Android] Chrome pans the page by the keyboard's height when typing into a focused TextField scrolled below the view
- **Action**: triage
- **Priority**: P2
- **Suggested assignee**: mdebbar
- **Labels to add**: triaged-web, P2
- **Labels to remove**: none
- **Reasoning**: it carries `a: text input`, but like #195774 last time, both the cause and the fix are in web engine view and viewport code rather than text editing, so it stays on `team-web`. It already has `has reproducible steps` and `workaround available`. No linked PR.
- **Root cause**: on Android the engine places the hidden `<input>` at the field's last-painted transform, through `AndroidTextEditingStrategy.placeElement`, even after the field has scrolled out of view. Chrome reveals the focused element on input by panning the visual viewport. Apps cannot opt into `interactive-widget=resizes-content`, because `_applyViewportMeta` in `full_page_embedding_strategy.dart` replaces the page's viewport meta and, since #191647, carries over only `viewport-fit`.
- **Potential solutions**: (1) Carry `interactive-widget` over from the page's meta the same way #191647 did for `viewport-fit`. (2) Clamp the hidden element to the visual viewport while the field is off-screen.

### #196861 - [web] "ViewInsets cannot be negative" at startup under Chrome's mobile device emulation: physical size is computed with a stale `visualViewport.scale`
- **Action**: triage
- **Priority**: P2
- **Suggested assignee**: mdebbar
- **Labels to add**: triaged-web, P2, has reproducible steps
- **Labels to remove**: none
- **Comment**: "Thanks for the analysis. A PR that reads `visualViewport.width`/`height` before the pixel ratio, or computes both from one snapshot, would be welcome. Please include a test that changes `visualViewport.scale` between the two reads."
- **Reasoning**: the assertion fires only in debug builds under DevTools device emulation and Playwright mobile presets, but that is how many developers test mobile layouts. Release builds get a wrong physical size until the next metrics change. mbcorona confirmed the read order on master. The reporter offered a PR.
- **Root cause**: `computePhysicalSize()` in `full_page_dimensions_provider.dart` reads `devicePixelRatio`, which includes `visualViewport.scale`, before it reads `visualViewport.width`. The width read forces a layout that changes the scale, so `computeKeyboardInsets()` sees a different ratio within the same resize.

### #196492 - [web] Tooltip text is read twice: while a tooltip shows, its target button's accessible name is doubled via aria-owns
- **Action**: triage, keep the routing
- **Priority**: P2
- **Suggested assignee**: flutter-zl
- **Labels to add**: triaged-web, P2, framework, found in release: 3.50
- **Labels to remove**: a: desktop
- **Reasoning**: it is already on `team-accessibility` with `fyi-web`, so the routing stays. Every Material `IconButton` with a tooltip is announced twice on hover. `a: desktop` is misleading, because a long press on touch triggers it too. No linked PR.
- **Root cause**: `RawTooltip` exposes the message both as `Semantics(tooltip:)` on the child and as un-excluded overlay `Text`. Since the `OverlayPortal` semantics refactor in #173005 and #178095, the overlay is a traversal child of the button, which the web engine maps to `aria-owns`. The button's name is computed from its contents, so the text is counted twice.
- **Potential solutions**: (1) Wrap the overlay's `tooltipBuilder` output in `ExcludeSemantics` when `semanticsTooltip` is non-empty. The reporter verified this on web. (2) If the overlay becomes `SemanticsRole.tooltip` per #161630, map it to `aria-describedby` instead of `aria-owns`. (3) Clear stale `aria-owns` when the traversal child is removed, which overlaps with #195016.

### #196633 - [web] A small looping animation costs more CPU and GPU the more static content is on screen, even behind a RepaintBoundary
- **Action**: triage
- **Priority**: P2
- **Suggested assignee**: harryterkelsen
- **Labels to add**: triaged-web, P2
- **Labels to remove**: none
- **Reasoning**: thorough measurements from a production app. Raster time per frame is 4 to 10 times higher with static content behind its own `RepaintBoundary`. Structural, not a break. The animation's own baseline cost is #118135, and the multi-threaded Skwasm row is probably #196484.
- **Root cause**: the web engine has no raster cache. A `RepaintBoundary` avoids re-recording the cards, but every frame still replays all retained pictures into the onscreen canvas, so the cost scales with everything on screen.
- **Potential solutions**: (1) A raster cache for picture layers that are unchanged across frames. (2) Partial repaint with a damage rect. (3) Keep long-lived static layers in their own canvases so the compositor reuses them.
