### CanvasKit, `team-web`

### #195093 - [web] CanvasKit: PathMetric.extractPath leaks the SkPath from getSegment, wasm heap grows until Aborted()
- **Action**: triage
- **Priority**: P1
- **Suggested assignee**: harryterkelsen
- **Labels to add**: triaged-web, P1, c: regression, c: crash, found in release: 3.47
- **Labels to remove**: none
- **Reasoning**: any app that draws dashed lines through `extractPath`, which includes fl_chart's `drawDashedLine`, grows the wasm heap by about 40 MB a second until CanvasKit aborts. The reporter traces it to #177686 in 3.47.0, and saurabh-mirajkar reproduced it on 3.47.7. He also saw growth on 3.44.9, so the regression label is worth a second look, but the crash alone justifies P1. Related: #187961.
- **PR review**: #195271 by rahulshahDEV, still a draft. It wraps `CkPathBuilder.fromSkPath` in a `try`/`finally` that calls `skPath.delete()`, which is exactly the missing call and matches what `CkPathBuilder.combine` already does. The test checks that the source path is deleted and the copy keeps its bounds. The new top-level `@visibleForTesting` helper is slightly heavier than an inline `try`/`finally` but harmless. It needs to leave draft and get a harryterkelsen review. If 3.44.9 also grows, there may be a second leak this PR does not cover.

### #195025 - [web] CanvasKit view goes blank after a few removeView/addView cycles in Safari: too many active WebGL contexts
- **Action**: triage
- **Priority**: P2
- **Suggested assignee**: harryterkelsen
- **Labels to add**: triaged-web, P2, c: regression, a: multi-view, browser: safari, found in release: 3.47
- **Labels to remove**: none
- **Reasoning**: reproduced by mbcorona on Safari with a code trace. It needs multi-view plus the multi-surface rasterizer, which Safari and Firefox use by default, so the reach is narrower than #195093. The reporter says 3.44.9 kept drawing, and points at the `onContextLost` rebuild from #180610 that became live once #185553 fixed its `LateInitializationError`. No linked PR.
- **Root cause**: `ViewRasterizer.dispose` disposes only the embedder, not the base canvas or cached overlays, and `_viewRasterizers`, `_createdSurfaces`, and the canvas provider's `_eventListeners` keep every removed view's objects. `CkSurface.dispose` frees only the `SkSurface` and never calls `deleteContext`, so the removed views' contexts stay live and the `onContextLost` rebuild keeps recreating them once the browser starts dropping the oldest.
- **Potential solutions**: (1) On view removal, dispose the view's surfaces fully: remove the canvas and listener, abandon and delete the `GrDirectContext`, call `deleteContext`, and drop the entry from the three collections. The reporter validated this in a patched build. (2) Skip the `onContextLost` rebuild for a disposed surface, as a quick stopgap that stops the runaway counter but frees nothing.

### #195290 - [Web] With semantics enabled, a focused TextField loses its text when its semantics node is merged into a new one
- **Action**: triage
- **Priority**: P1
- **Suggested assignee**: flutter-zl
- **Labels to add**: triaged-web, P1, engine, platform-web, found in release: 3.47
- **Labels to remove**: none
- **Reasoning**: user data loss in a focused text field, same severity as #194636 last week. Reproduced on master by suryaKommana2662. No PR references it directly, but your #195141 probably fixes it.
- **Root cause**: when the field's semantics merge into a new node, the old `SemanticTextField` is disposed and `SemanticsTextEditingStrategy.disable()` drops `lastEditingState`, so the new empty `<input>` sends `""` to the framework. This is the #194636 mechanism with a different trigger.
- **Potential solutions**: (1) Verify #195141 against this repro, and if it passes add `Fixes #195290` to that PR. (2) If it does not, seed the new `<input>` from `semanticsObject.value`, which #195445 now does for non-active fields.

### #195289 - [Web] With semantics enabled, a focused TextField loses focus when a semantics node is inserted above it
- **Action**: triage
- **Priority**: P2
- **Suggested assignee**: flutter-zl
- **Labels to add**: triaged-web, P2, engine, platform-web, found in release: 3.47
- **Labels to remove**: none
- **Reasoning**: reproduced by suryaKommana2662. A tooltip hover inside a go_router `ShellRoute` is enough to trigger it, so it is easy to hit in real apps, but the reporter has a workaround and no text is lost. No linked PR.
- **Root cause**: `SemanticsObject.updateChildren` moves the existing ancestor element into the new node with `append` or `insertBefore`. Moving a focused element blurs it with no `relatedTarget`, the focus lands on `<body>`, and `ViewFocusBinding` reports the view as unfocused.
- **Potential solutions**: (1) In `updateChildren`, note whether `document.activeElement` is inside a subtree being moved and refocus it with `preventScroll` after the move. (2) Have the semantics text editing strategy ignore a blur with no `relatedTarget` while the element is still connected and the connection is open, then refocus it.

### #195291 - [Web] With semantics enabled, a click inside a TextFieldTapRegion stops typing in the focused TextField
- **Action**: triage
- **Priority**: P2
- **Suggested assignee**: flutter-zl
- **Labels to add**: triaged-web, P2, engine, platform-web, found in release: 3.47
- **Labels to remove**: none
- **Reasoning**: clear repro and analysis. It breaks formatting toolbars built with `TextFieldTapRegion` once semantics is on. The framework still thinks the field is focused, so the caret keeps blinking while typing goes nowhere. No linked PR.
- **Root cause**: the mousedown on the text's semantics element moves browser focus to `flutter-view`. The `SemanticTextField` blur listener calls `SemanticsTextEditingStrategy.deactivate`, and nothing reactivates it because the framework focus never changed. The default strategy refocuses its `<input>` on the same blur.
- **Potential solutions**: (1) Match the default strategy: on blur, refocus the `<input>` while the connection is still open and the field is still the active text field. (2) Call `preventDefault` on mousedown over non-focusable semantics nodes while a semantics text field is focused, as the reporter's workaround does. This fix also covers #195289 if done as a shared blur handler.

### #195469 - [web] SemanticScrollable keeps its scroll adjustment after the list stops scrolling, so taps land on the wrong row
- **Action**: triage
- **Priority**: P2
- **Suggested assignee**: flutter-zl
- **Labels to add**: triaged-web, P2, engine, platform-web, found in release: 3.47
- **Labels to remove**: platform-macos, platform-linux
- **Reasoning**: reproduced on master by suryaKommana2662. With semantics on, clicks activate the wrong row, which is bad, but it only happens after a scrolled list shrinks to non-scrollable. The `platform-macos` and `platform-linux` labels describe the host OS, not the target. This is a separate defect from #194549 per the reporter. No linked PR.
- **Root cause**: when the list can no longer scroll, `SemanticScrollable.update` takes the `!_canScroll` branch, calls `_cleanUp()` and returns. Nothing resets `verticalScrollAdjustment` or `scrollTop`, so children keep a stale translate and the browser clamps `scrollTop` against the translated overflow.
- **Potential solutions**: (1) In `_cleanUp()` or the `!_canScroll` branch, reset `verticalScrollAdjustment` and `horizontalScrollAdjustment` to 0, set `scrollTop` and `scrollLeft` to 0, and re-run child positioning. (2) Fix it together with #194549, since both live in the same update path.

### #195215 - [web][a11y] A Slider enabled after its first frame has no aria-valuetext (its input reads "50") until its value changes
- **Action**: triage
- **Priority**: P2
- **Suggested assignee**: flutter-zl
- **Labels to add**: triaged-web, P2, engine, platform-web, found in release: 3.47
- **Labels to remove**: none
- **Title cleanup**: `[web][a11y] Slider enabled after first frame exposes no aria-valuetext, min, or max until its value changes`
- **Reasoning**: reproduced on master by suryaKommana2662. A screen reader hears "50" for any slider that starts disabled, a common filter-sheet pattern. No linked PR.
- **Root cause**: enabling the slider adds the increase and decrease actions, so a new `SemanticIncrementable` is created for a node whose `value`, `increasedValue`, and `decreasedValue` were set earlier. `_pendingResync` starts `false` and none of those fields is dirty, so `_updateInputValues()` returns early and never writes the attributes. #187217 did not cover a role created for an existing node.
- **Potential solutions**: (1) Initialize `_pendingResync` to `true` in the `SemanticIncrementable` constructor so the first `update()` always writes the input. (2) Call `_updateInputValues()` unconditionally on the role's first update.

### Text input, on `team-text-input` + `fyi-web`

### #195443 - [web] iOS Safari: Japanese IME duplicates composed text in a TextField with enableInteractiveSelection: false
- **Action**: triage
- **Priority**: P2
- **Suggested assignee**: mdebbar
- **Labels to add**: triaged-web, P2, engine, browser: safari, found in release: 3.47
- **Labels to remove**: none
- **Reasoning**: reproduced on master by suryaKommana2662, who also saw delete add text. It breaks Japanese input on iOS Safari for any field with selection disabled, a common setting for PIN and search fields. Keeps its `team-text-input` routing. No linked PR.
- **Root cause**: `IOSTextEditingStrategy` routes `input` and `selectionchange` to `DefaultTextEditingStrategy.handleChange`, which first calls `suppressInteractiveSelectionIfNeeded`. That collapses the non-collapsed selection WebKit holds over the marked text and writes it back with `applyToDomElement` synchronously, with no check for an active composition. WebKit then stops treating the text as marked and never fires `compositionend`.
- **Potential solutions**: (1) Skip `suppressInteractiveSelectionIfNeeded` while a composition is active, using the strategy's composing state or the `InputEvent.isComposing` flag. (2) Defer the collapse until `compositionend`.
